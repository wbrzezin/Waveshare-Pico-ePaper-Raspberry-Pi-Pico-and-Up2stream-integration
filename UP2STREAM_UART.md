# UP2Stream UART Protocol Notes

Technical documentation of the UART communication observed on an
Arylic UP2Stream Pro and used by the **UP2Stream Display** project.

This document combines:

- information from the published UP2Stream UART protocol documentation,
- observations made with a physical UART analyzer,
- behavior observed on the tested UP2Stream Pro,
- implementation conclusions relevant to this project.

> **Important**
>
> This document is not intended to be a complete or authoritative
> specification of the UP2Stream UART protocol.
>
> Some commands described in the published protocol documentation do not
> behave as expected on the tested device.
>
> Unless explicitly stated otherwise, observations in this document refer
> to an Arylic UP2Stream Pro running firmware:
>
> `35-99e42697-6`

---

# 1. UART Configuration

The UART interface uses:

| Parameter | Value |
|---|---|
| Baud rate | 115200 |
| Data bits | 8 |
| Parity | None |
| Stop bits | 1 |
| Flow control | None |

In short:

```text
115200 8N1

Messages are terminated with a semicolon:

VOL:46;

The UART interface is bidirectional:

MCU → UP2Stream
UP2Stream → MCU
2. Important Communication Characteristics

The UP2Stream UART interface should be treated as an asynchronous
message stream, rather than a simple request/response protocol.

There are two important classes of messages:

commands which can be actively queried by the MCU,
asynchronous messages generated by the UP2Stream itself.

This distinction is important for the implementation of the parser.

3. Queryable Device State

The tested device responds reliably to commands requesting the current
device state.

Examples:

STA;
SRC;
PLA;
VOL;
MUT;
AUD;
CHN;
LPM;
NAM;
VER;
ETH;
TME;

For example:

STA;

returns:

STA:NET,0,46,2,4,1,1,1,1,0;

Similarly:

SRC;

returns:

SRC:NET;

These commands can therefore be used by the MCU to actively synchronize
the state of the UP2Stream.

4. Playback Metadata

Playback-related information is transmitted by the UP2Stream as
asynchronous messages.

Observed message types include:

TIT:
ART:
ALB:
VND:
ELP:

Examples:

TIT:Komandor Tarkin;
ART:Kazik;
ALB:Melassa;
VND:spotify;
ELP:3551/0;
ELP:7117/254026;

These messages describe the currently playing content and playback
position.

Important

On the tested firmware, playback metadata should not be treated as
normal queryable device state.

In particular, sending:

ART;

does not reliably result in:

ART:...

Likewise, TIT;, ALB;, VND; and ELP; should not be assumed to
return the current playback metadata.

The application therefore treats these messages as asynchronous
notifications.

5. Asynchronous UART Stream

The UP2Stream can transmit messages independently of commands sent by
the MCU.

During playback, for example, the device periodically generates:

ELP:47762/762946;
ELP:53100/762946;
ELP:59551/762946;
ELP:75899/762946;
ELP:81373/762946;

At the same time, the MCU may send a query such as:

STA;

Therefore:

The next received UART message must not be assumed to be the response
to the last command sent by the MCU.

For example, if the MCU sends:

ART;

and the next received message is:

ELP:4168/239360;

this does not prove that ART; returned an ELP response.

The ELP message may simply be an asynchronous message generated by the
UP2Stream at the same time.

Parser requirement

The parser must classify every received message independently according
to its prefix:

STA:  → system state
SRC:  → source
PLA:  → playback state
VOL:  → volume
MUT:  → mute
TIT:  → title
ART:  → artist
ALB:  → album
VND:  → playback provider
ELP:  → elapsed/total playback time
TME:  → device time

The parser must not depend on request/response ordering.

6. SYS — System State

The following messages were observed:

SYS:ON;

and:

SYS:STANDBY;

A long press of the physical power button produced:

SYS:STANDBY;
MUT:1;
VOL:30;

This allows the application to detect the transition into standby.

7. STA — Complete Device State

The STA message contains a number of device state parameters.

Example:

STA:NET,0,46,2,4,1,1,1,1,0;

According to the protocol documentation, the fields are:

Field	Example	Meaning
source	NET	current source
mute	0	mute state
volume	46	volume
treble	2	treble
bass	4	bass
net	1	network state
internet	1	Internet state
playing	1	playback state
led	1	LED state
upgrading	0	firmware upgrade state

The query:

STA;

was confirmed to return the current state on the tested device.

Example interpretation
STA:NET,0,46,2,4,1,1,1,1,0;

means:

Source     = NET
Mute       = 0
Volume     = 46
Treble     = 2
Bass       = 4
Network    = 1
Internet   = 1
Playing    = 1
LED        = 1
Upgrading  = 0

STA is particularly useful as a periodic state synchronization
mechanism because a single query provides many parameters.

8. SRC — Current Source

Observed messages include:

SRC:NET;
SRC:BT;
SRC:LINE-IN;

The physical source button was observed to cycle through different
inputs.

The protocol documentation lists the following source values:

NET
USB
USBDAC
LINE-IN
LINE-IN2
BT
OPT
COAX
I2S
HDMI

The query:

SRC;

returns the current source.

9. PLA — Network Playback State

Observed values:

PLA:0;
PLA:1;

The query:

PLA;

returns the current network playback state.

The UP2Stream Display project uses this information for the playback
indicator:

PLA:1 → playing
PLA:0 → paused / not playing

This is also used by the display logic to select between the PLAY and
PAUSE icons.

10. VOL — Volume

Observed messages:

VOL:30;
VOL:46;

The query:

VOL;

returns the current volume.

The documented range is:

0 ... 100

The protocol also allows setting the volume:

VOL:50;

The UP2Stream Display project currently uses VOL to display the
current volume.

11. MUT — Mute

Observed messages:

MUT:1;
MUT:0;

The device may temporarily mute the output while changing sources.

For example:

MUT:1;
SRC:BT;
MUT:0;
VOL:30;

The query:

MUT;

returns the current mute state.

The protocol also supports:

MUT:0;
MUT:1;
MUT:T;

where T represents toggle.

12. AUD — Audio Output

Observed:

AUD:1;

The query:

AUD;

returns the current audio output state.

13. CHN — Channel State

The query:

CHN;

was observed to return:

CHN:S;

The documented values are:

L
R
S

representing left, right and stereo channel state.

14. LPM — Loop Mode

Observed:

LPM:REPEATALL;

and:

LPM:SEQUENCE;

The documented loop modes are:

REPEATALL
REPEATONE
REPEATSHUFFLE
SHUFFLE
SEQUENCE

The query:

LPM;

returns the current loop mode.

15. TIT — Current Track Title

The UP2Stream sends the title of the currently playing track:

TIT:Komandor Tarkin;

Another observed example:

TIT:Moritet von Mackie Messer;

The device sends TIT: when the playback content changes.

15.1. Title length limitation

The physical UART analyzer showed that long titles may be truncated.

For example, the full title was:

Pieśń w której Mackie prosi wszystkich o przebaczenie - Wersja z pętlą

while the UART output contained:

TIT:Pieśń w której Mackie prosi wszystkich o przebaczenie - Wers;

The application therefore uses a practical title length limit of
approximately 60 characters.

This is not considered a problem for the current project.

16. Embedded ELP Message in TIT

An important behavior was observed where the UP2Stream concatenates
messages.

For example, a received buffer may contain:

TIT:Ballada oELP:31880/137426;

The title does not actually contain ELP:.

Instead, the next message has been appended directly to the title.

The project parser therefore searches the contents of a TIT: message
for an embedded:

ELP:

and processes that section as a separate ELP message.

This behavior must be preserved when modifying the parser.

17. ART — Current Artist

The UP2Stream may send:

ART:Kazik;

when the playback content changes.

However, testing showed that ART: is not guaranteed to accompany
every TIT: message.

For example, the following sequence has been observed:

TIT:...;
ALB:...;

without:

ART:...;

The application therefore must not assume that the artist will always
be received together with the title.

The current artist value should remain unchanged until a new ART:
message is received.

Sending:

ART;

does not reliably return the current artist on the tested firmware.

18. ALB — Current Album

The UP2Stream may send:

ALB:Melassa;

when playback content changes.

As with ART:, the presence of ALB: should not be assumed for every
track change.

The application should process ALB: independently whenever it is
received.

19. VND — Playback Provider

The UP2Stream may send:

VND:spotify;

This identifies the provider/source of the currently playing content.

This is more specific than:

SRC:NET;

For example:

SRC:NET;
VND:spotify;

means that the general source is network playback and the content
provider is Spotify.

VND: is a useful candidate for future display functionality.

20. ELP — Elapsed / Total Playback Time

The ELP format is:

ELP:{elapsed}/{total};

The values are expressed in seconds.

Examples:

ELP:2403/239360;
ELP:33500/762946;
ELP:1028/762946;

The UP2Stream periodically transmits ELP: during playback.

The UP2Stream Display project uses this information to calculate:

current playback time,
total track duration,
progress percentage.
Important

ELP is normally not queried by the project.

The device already generates these messages periodically.

21. TME — Device Time

The UP2Stream supports the query:

TME;

The tested device responds with:

TME:2026-08-10 18:37:05 (+1);

The response contains:

YYYY-MM-DD HH:MM:SS (offset)

The UP2Stream synchronizes its internal clock with the smartphone
application.

21.1. Daylight Saving Time

Testing in Poland showed that the UP2Stream does not correctly
automatically apply the European daylight-saving-time change.

For example, during Polish summer time the correct local offset is:

UTC+2

while the tested UP2Stream may report:

(+1)

Therefore TME should not currently be treated as the final local
display time without applying an application-side timezone correction.

21.2. Planned project usage

The intended architecture is:

UP2Stream
    │
    │ TME;
    ▼
TME response
    │
    ▼
Pico RTC
    │
    ▼
local timezone / DST correction
    │
    ▼
clock display

The existing Pico RTC can continue to maintain the time between
synchronizations.

22. NAM — Device Name

Observed:

NAM:55703273747265616D5F50726F;

The value is encoded as hexadecimal UTF-8.

Decoded:

Up2stream_Pro

The query:

NAM;

returns the device name.

23. VER — Firmware and API Version

Observed:

For the tested device:

Firmware = 35
Commit   = 99e42697
API      = 6

This information can be useful when comparing behavior between
different firmware versions.

26. ERR:INVALID

During testing, the device occasionally returned:

ERR:INVALID;

This was observed while experimenting with commands from the published
protocol documentation.

This confirms that the documented command set should be treated as a
protocol reference rather than a guarantee that every command is
supported by every firmware version or device model.

27. Startup Sequence Observed

A typical startup sequence observed on the physical UART analyzer was:

SYS:ON;
MUT:1;
VER:35-99e42697-6;
STA:NET,1,46,2,4,0,0,0,1,0;
VOL:46;
MUT:0;
VOL:46;

After a short delay:

AUD:1;
LPM:REPEATALL;
NAM:55703273747265616D5F50726F;
VOL:46;
NET:1;
WWW:1;

The exact order and timing of messages should not be considered
guaranteed.

28. Source Switching Observed

A short press of the physical power/source button produced:

MUT:1;
SRC:NET;
PLA:0;
MUT:0;
VOL:46;

Another press:

MUT:1;
SRC:BT;
MUT:0;
VOL:30;

Another press:

MUT:1;
SRC:LINE-IN;
MUT:0;
VOL:30;

This demonstrates that changing the source can generate several
messages, not just a single SRC: message.

29. Standby Observed

A long press of the physical power button produced:

SYS:STANDBY;
MUT:1;
VOL:30;

The application can therefore use SYS:STANDBY as an indication that
the device has entered standby mode.

30. Recommended Parser Design

The UART parser should be implemented as an asynchronous stream parser.

It should:

collect incoming bytes until the message terminator ;,
identify the message type from its prefix,
parse the message independently,
update only the corresponding fields in PlayerState,
never assume that the next message is the response to the last
command sent.

Conceptually:

UART byte stream
       │
       ▼
message framing
       │
       ▼
message type detection
       │
       ├── STA → system state
       ├── SRC → source
       ├── PLA → playback state
       ├── VOL → volume
       ├── MUT → mute
       ├── TIT → title
       ├── ART → artist
       ├── ALB → album
       ├── VND → provider
       ├── ELP → playback time
       └── TME → device time
31. Project-Specific Handling of Missing Metadata

Because the UP2Stream may not transmit all metadata fields for every
track change, the application should not clear all metadata whenever
TIT: is received.

For example, receiving:

TIT:New Title;

does not mean that:

ART:
ALB:
VND:

are unavailable.

The application should update only:

title

and retain the previously known:

artist
album
provider

until corresponding messages are received.

32. Periodic State Synchronization

The reliable query interface makes it possible to periodically
synchronize the state of the device.

A single:

STA;

query can provide:

source
mute
volume
treble
bass
network
internet
playing
LED
upgrading

This can be used as a lightweight watchdog/state synchronization
mechanism.

For example, the project may periodically send:

STA;

without relying on unsolicited messages to recover all device state.

Playback metadata should remain asynchronous.

36. Testing Method

Protocol behavior was investigated using a physical UART analyzer
connected directly to the UP2Stream Pro.

This method was used to distinguish:

messages generated by the device automatically,
responses to commands,
timing/order of messages,
missing metadata,
message concatenation,
unsupported commands.

The physical UART capture is considered the primary source of truth for
the behavior of the tested hardware.

37. Summary of Important Findings

The most important findings for this project are:

UART communication uses 115200 8N1.
Messages are terminated by ;.
The UART stream is asynchronous.
Device-state commands such as STA;, SRC;, PLA;, VOL; and
MUT; can be actively queried.
Playback metadata such as TIT:, ART:, ALB: and VND: is
transmitted asynchronously.
ART: is not guaranteed to be transmitted for every track.
ELP: is transmitted periodically by the device during playback.
TIT: may be truncated.
TIT: may contain an embedded ELP: message because of message
concatenation.
TME; provides the device's current date and time.
The device synchronizes its clock with the smartphone application.
The tested device does not automatically handle the Polish
daylight-saving-time offset correctly.
STA; is a particularly useful command for periodic state
synchronization.
The parser must never assume that the next received message is the
response to the last command sent.
The behavior of the actual firmware should take precedence over
assumptions based solely on the published protocol documentation.
